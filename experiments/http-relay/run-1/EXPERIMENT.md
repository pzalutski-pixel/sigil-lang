## Purpose

Compare AI-assisted software development across language paradigms:
1. **Sigil (no examples)** - Grammar + contracts only, no usage examples
2. **Sigil (with examples)** - Grammar + contracts + example code access
3. **C++** - Traditional compiled language (in LLM training data)
4. **Python** - Interpreted language (in LLM training data)

The two Sigil variants test whether example access compensates for lack of training data.

## Hypothesis

An AI-native language with explicit, unambiguous grammar and machine-readable contracts will result in:
- Fewer errors and rework cycles
- More predictable code generation
- Better first-attempt success rate

Despite the token overhead of loading grammar/spec upfront (Sigil's "handicap").

## Test Application: HTTP File Relay

```
[Producer]                    [Consumer]
    |                              |
    | 1. Read input.txt            |
    | 2. POST to :9753 ----------->|
    |                              | 3. Prepend timestamp + marker
    |                              | 4. Write output.txt
```

**Why This Test:**
- File I/O: Tests system interaction
- HTTP: Tests networking
- Processing: Tests basic logic
- Error handling: Tests robustness

## Handicap Acknowledgment

**Sigil prompt includes:** References to grammar documentation and stdlib contracts. This consumes tokens upfront but provides complete, unambiguous specification.

**C++ and Python:** Rely only on LLM training data (may be incomplete, outdated, inconsistent).

## Why Two Sigil Variants?

**The fairness problem:** C++ and Python benefit from LLM training data containing millions of code examples showing patterns like "how to write an HTTP server" or "how to read a file". Sigil has zero training examples - the AI has never seen Sigil code before.

**Sigil (no examples):** Tests the pure hypothesis - can explicit grammar + contracts alone enable correct code generation? This is the harder test but measures the value of unambiguous specification.

**Sigil (with examples):** Allows access to `examples/` folder, analogous to C++/Python's training data advantage. Tests whether examples help close the gap.

Comparing both variants reveals:
- How much examples matter vs. grammar alone
- Whether Sigil's explicit design helps even without examples
- The "learning curve" cost of a new language

## Hypothesis Result: NOT CONFIRMED

The hypothesis that an AI-native language with explicit grammar would result in fewer errors was **not confirmed** by this experiment. Python and C++ both achieved zero rework with first-attempt success, while both Sigil variants required multiple iterations.

However, this comparison is **fundamentally unfair** - Python and C++ have extensive training data, while Sigil has zero. The AI had never seen Sigil code before this experiment.

## Key Observations

### 1. Training Data Dominance
The most striking result is Python's efficiency: **3.4k tokens with zero rework**. This demonstrates the massive advantage of training data. The AI didn't need to "learn" Python - it already knew HTTP server patterns from millions of examples.

### 2. Sigil Did Work
Despite zero training data, both Sigil variants **successfully completed the task**. The AI learned the language entirely from in-context documentation. This proves that explicit, unambiguous grammar CAN enable AI code generation for unknown languages.

### 3. Examples: Mixed Blessing
Counter-intuitively, the "with examples" variant performed **worse** than "no examples":
- Used more tokens (90k vs 70.8k)
- Had more AI logic bugs (3 vs 0)
- Required user intervention

Examples reduced language learning issues (5→1) but introduced **pattern-copying without understanding**. The "no examples" AI had to reason from first principles and made fewer logic errors.

### 4. Hash Computation: Tooling Problem
6 of 12 rework cycles in "no examples" were hash-related. This is a **tooling friction**, not a language design flaw. The `--fix-hashes` compiler flag exists but wasn't used. A standalone hash utility would eliminate this entirely.

### 5. Compiler Strictness: Feature Not Bug
The Sigil compiler's strict OUTPUT analysis caught real bugs (missing writes on some paths). This is the **intended behavior** - the compiler enforces correctness. These aren't "errors" so much as the compiler doing its job.

### 6. Stdlib Underutilization
The "no examples" AI reimplemented `htons`, `int-to-string`, and `format-time` manually instead of using stdlib. Better contracts.registry documentation or IDE integration could help here.

## Fair Comparison Attempt

Excluding reference reading (which trained languages get "for free"):

| Language | Coding Tokens | Ratio vs Python |
|----------|---------------|-----------------|
| Python | 3.4k | 1x |
| C++ | 10.4k | 3x |
| Sigil (no examples) | 38k | 11x |
| Sigil (with examples) | 42k | 12x |

Even with adjustment, Sigil requires ~11x more coding effort. But this is comparing:
- **Trained language** (billions of examples) vs **Untrained language** (zero examples)
- **High-level stdlib** (`http.server`) vs **Low-level behaviors** (manual socket operations)

## Honest Assessment

### What Worked
- Grammar was sufficient to learn language from scratch
- Compiler errors were helpful and actionable
- Both Sigil variants eventually succeeded
- Zero AI logic bugs in "no examples" variant

### What Didn't Work
- Hash computation is tedious and error-prone
- More tokens != better results (with-examples was worse)
- Significant efficiency gap vs trained languages
- AI didn't discover/use all stdlib behaviors

### Surprising Findings
- Examples can hurt more than help (pattern-copying)
- Thinking from first principles (no examples) led to fewer logic bugs
- Python was 3x more efficient than C++ despite both being trained

## Recommendations

### For Sigil Development
1. **Add hash utility** - Standalone tool or IDE integration to compute hashes
2. **Improve stdlib discovery** - Better documentation or tooling to find relevant behaviors
3. **Consider higher-level abstractions** - `http.server` equivalent would reduce boilerplate

### For Future Experiments
1. **Multiple trials** - Single test has high variance
2. **Different tasks** - HTTP relay may favor high-level languages
3. **Measure correctness** - Not just completion, but bug rates in resulting code
4. **Control for AI randomness** - Same prompt can yield different results

## Final Thoughts

This experiment does not prove Sigil is "better" or "worse" than Python/C++. It demonstrates that:

1. **Training data matters enormously** - The efficiency gap is real
2. **Explicit grammar enables learning** - AI can learn unknown languages from docs
3. **Examples aren't always helpful** - Can encourage shallow pattern-matching
4. **Tooling friction is real** - Hash computation needs automation
5. **Compiler strictness is valuable** - Caught real bugs at compile time

The original hypothesis about "fewer errors" assumed a level playing field. With zero training data, Sigil was always at a disadvantage. A fairer test would compare Sigil after significant training data exists - but that defeats the purpose of testing "AI-native" design.

Perhaps the real question isn't "does Sigil reduce errors?" but "can AI learn new languages from explicit specifications?" The answer to that is **yes**.
